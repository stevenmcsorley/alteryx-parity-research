# Tool status rules

All statuses are generated by `scripts/build_status.py`; editing `implementation_status`/`verification_status` by hand is a review failure (`tests/test_research_coverage.py` checks agreement with `data/tool-status.json`, and CI runs `build_status.py --check`).

| Field | Value | Rule |
|---|---|---|
| implementation_status | `implemented` | A flowengine kernel claims the catalogue id **and** ≥1 test exercises that kernel (recorded at run time) **and** all of those tests pass |
| | `in-progress` | A kernel is registered but tests are missing or failing |
| | `not-started` | No kernel; executing the entry fails validation with `tool-unavailable` |
| verification_status | `partial` | ≥1 differential reference case exists and all pass (on the build in the results file) |
| | `failed` | Any differential case fails |
| | `not-tested` | No differential case |
| | `verified` | Never automatic. Requires: cases covering every configuration option in the tool's contract, error contracts, null/type/order edge cases, and a recorded human review |
| external_prerequisites_blocking | true | Category rule says exact behaviour depends on licensed datasets, vendor cloud services, external accounts or LLM providers |

Per-entry evidence lives in `tool-contracts/<category>/<slug>.contract.json` (schema: `schemas/tool-contract.schema.json`): anchors with provenance (`flowengine-manifest`, `reference-observed`, `public-doc-extracted`), configuration schema or observed configuration element names, dependencies, the tests that exercise the kernel, conformance cases with evidence pointers, and unresolved questions.
